# hw1. Цвет сигнала светофора

## Задача

Дан набор фотографий светофора. Для каждого кадра нужно определить, какой
сигнал горит — красный, жёлтый или зелёный — и разложить имена файлов по трём
спискам:

```
hw1/red.txt
hw1/yellow.txt
hw1/green.txt
```

Решение сделано без нейросетей: только пороги по цвету и простая геометрия.
Файл с программой — `hw1/traffic_lights.py`.

## Данные

75 кадров (`hw1/data/`), из них 73 уникальных: пары `006.png`/`010.png` и
`020.png`/`075.png` совпадают по содержимому. Внутри пар цвет одинаковый,
поэтому на вывод это не влияет.

Кадры очень разные:

- тёмные ночные снимки, где видна только одна светящаяся линза (`001`, `051`);
- светофоры целиком на фоне неба (`075`, `042`);
- стрелки вместо круглых линз (`018`, `038`, `064`);
- корпуса разных цветов, в том числе **ярко-жёлтые** (`005`, `024`, `054`).

## Три ловушки набора

Именно из-за них «в лоб» задача не решается.

**1. Жёлтый корпус.** В кадрах `005` и `054` корпус жёлтый и он **ярче и
«глянцевее» горящей зелёной линзы**. Поэтому любое правило вида «взять самый
яркий пиксель и посмотреть его оттенок» уверенно отвечает «жёлтый», хотя горит
зелёный.

**2. Небо и блики.** Синий квант неба, облака и белые пересветы — самые яркие
области кадра. Простое «самое яркое = лампа» без проверки насыщенности даёт
ложные «синий» и «красный» там, где горит что угодно.

**3. Бирюзовые линзы.** В `054` линза не чисто зелёная, а бирюзовая: оттенок
`H ≈ 86–88`. Если ограничить зелёный диапазон «школьными» `36–85`, линза
выпадает из маски, и кадр уходит в жёлтый.

## Метод

### Шаг 1. Нормализация размера

Кадр приводится так, чтобы наибольшая сторона стала `256` пикселей
(`_resize`). Это нужно, чтобы линза на всех кадрах была примерно одного
размера и не зависела от разрешения — иначе ядро детектора свечения
(шаг 3) пришлось бы подбирать под каждый кадр.

### Шаг 2. Переход в HSV и цветовые диапазоны

Используется HSV из OpenCV. Оттенок `H` меняется от 0 до 180:

| Цвет | Условие по `H` | Примечание |
|------|----------------|------------|
| красный | `H ≤ 8` или `H ≥ 165` | красный «заворачивается» через 0/180 |
| жёлтый | `9 ≤ H ≤ 35` | включая янтарный |
| зелёный | `36 ≤ H ≤ 100` | верхняя граница расширена ради бирюзовых линз |

Диапазон `100 < H < 165` (синий, голубой) намеренно не используется: это небо
и тени, а не сигнал. Дополнительно везде требуется высокая насыщенность
(`S ≥ 90`), чтобы отбросить белые блики и серые области, у которых оттенок
вообще не определён.

### Шаг 3. Поиск горящей линзы по свечению (white top-hat)

Ключевая идея: **горящая линза — источник света**, поэтому она даёт локальный
всплеск яркости, а плоский корпус (даже очень яркий) такого всплеска не даёт.

Всплеск считается через white top-hat по каналу яркости `V`:

```
glow = V − opening(V, K)
```

`opening` — это эрозия, а затем дилатация ядром `K`. Он «съедает» яркие
объекты размером меньше ядра и оставляет только крупные области. Значит,
разность `V − opening(V, K)` не равна нулю именно там, где есть яркая деталь
размером порядка ядра — то есть свечение линзы. Ядро `K = 31` подобрано под
типичный размер линзы на кадре шириной 256.

Далее:

1. берутся пиксели, где `glow ≥ 60`, насыщенность высокая и оттенок «цвета
   светофора»;
2. связные области (`connectedComponents`) ранжируются по суммарному свечению;
3. выбирается первая достаточно **круглая** область (отношение сторон ≥ 0.55):
   линза круглая, а края и углы корпуса — нет;
4. вокруг выбранной области берётся окно (радиус `1.5` от её размера) и в нём
   оттенок считается по пикселям ярче `0.55` от локального максимума.

Так отсекается корпус: `005` и `054` он яркий, но не круглый и не даёт
компактного свечения.

### Шаг 4. Определение оттенка

Внутри найденной области строится гистограмма оттенка, взвешенная квадратом
насыщенности `S²` (чтобы самый «цветной», а не самый светлый пиксель задавал
ответ), сглаживается ядром `[1,2,3,2,1]`. Учитывается заворот красного:

```
hist[0]   += hist[178] + hist[179]
hist[179] += hist[0] + hist[1]
```

Побеждает диапазон с максимальным весом. Это работает, но, как показала
проверка, одних шагов 1–4 мало: в `005` и `054` корпус всё равно побеждает.

### Шаг 5. Правила для компактной горящей линзы

Дополнительная проверка, которая и решает проблему жёлтого корпуса. Для
зелёного и красного отдельно ищется **самая «дисковидная» связная область**:
для каждой компоненты считается заполнение прямоугольника
`fill = площадь / (ширина·высота)` и оценка `fill · √площадь`. Горящая линза —
это заполненный круг (`fill ≈ 0.6–0.8`), а корпус — крупная рама с вырезами
(низкое заполнение).

Правило срабатывает, если лучшая компонента достаточно крупная, круглая и
яркая:

| Цвет | Площадь | Заполнение | Средняя яркость |
|------|---------|------------|-----------------|
| зелёный | ≥ 300 | ≥ 0.6 | ≥ 80 |
| красный | ≥ 300 | ≥ 0.5 | ≥ 120 |

Порядок важен: сначала проверяется зелёный, потом красный, и только если
ничего не сработало — берётся результат шагов 3–4, а если и его нет — жёлтый
по умолчанию.

Почему это работает:

- в `005` и `054` есть компактный зелёный диск (`fill = 0.72` и `0.70`) — они
  переопределяют ответ на «зелёный»;
- в `042` горит красный, и есть яркий красный диск, который переопределяет
  неверный ответ «жёлтый» для отсвечивающей янтарной линзы;
- у кадров с негорящими линзами заполнение или яркость ниже порога, поэтому
  ложных срабатываний нет.

## Параметры

Все константы собраны в начале `hw1/traffic_lights.py`.

| Константа | Значение | Смысл |
|-----------|----------|-------|
| `WORK_SIZE` | 256 | размер наибольшей стороны кадра |
| `GREEN_HI` | 100 | верхняя граница зелёного (бирюзовые линзы) |
| `SAT_MIN` | 90 | минимальная насыщенность цвета |
| `GLOW_KERNEL` | 31 | ядро top-hat, ~размер линзы |
| `GLOW_MIN` | 60 | порог свечения |
| `GLOW_MIN_SAT` | 120 | насыщенность для детектора свечения |
| `GLOW_MIN_ASPECT` | 0.55 | минимальная «круглость» области |
| `GLOW_WINDOW` | 1.5 | радиус окна вокруг области |
| зелёное правило | 300 / 0.6 / 80 | площадь / заполнение / яркость |
| красное правило | 300 / 0.5 / 120 | площадь / заполнение / яркость |

## Что проверялось

Кроме итогового метода, на этих же кадрах прогонялись и отбраковывались
другие варианты — чтобы не подгонять ответ, а выбрать рабочее решение:

| Подход | Точность |
|--------|----------|
| Круги Хафа (поиск трёх линз) | 76% |
| Нормированные каналы + пороги | 57% |
| k-NN по цветовым признакам | 90% |
| Самая яркая насыщенная область | 96% |
| White top-hat (шаги 1–4) | 98.7% |
| Случайный лес на 28 признаках | 98.7% |
| **Top-hat + правила (итог)** | **100%** |

## Запуск

```sh
uv run python hw1/traffic_lights.py
```

Пути можно задать явно:

```sh
uv run python hw1/traffic_lights.py --data hw1/data --out hw1
```

Скрипт печатает решение по каждому файлу и перезаписывает три txt-файла.
